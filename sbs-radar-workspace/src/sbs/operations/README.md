# Incremental refresh — SK11

`plan = load_sealed_plan(project_root)` verifies the two captured manifests and all six original PDF hashes. `RefreshRunner(plan, isolated_state_root)` uses exact configured source URLs. No scan, inference, import-time network or resource creation occurs. Captured manifest and PDF paths are resolved through `project_path`: the exact historical project root is rebased into the supplied snapshot and hashes are checked there. Missing snapshot inputs fail instead of falling back to the original repository. External paths and traversal are rejected.

`bootstrap_capture()` creates an explicitly partial **capture-only** baseline in isolated state using real SK02 ingest/extract. It does not certify a runtime release. `run(run_id=...)` defaults to sealed-byte reuse. Pass the existing SK02 `fetch_pdf` explicitly as `fetcher` only for an authorized fresh HTTPS GET run; no POST is implemented. A trusted injected test fetcher is possible but must not be described as live acquisition. The result counts `fetch_attempts`; exact wire-level `network_requests` is null for an injected acquisition adapter (which may redirect or be a fixture), and zero for sealed reuse. Each configured source is attempted at most once; SK02 owns its safe redirect and timeout policy. Caps bound source count, aggregate bytes (reserve one maximum PDF before network fetch), and elapsed checkpoints. Synchronous hooks/extraction cannot be interrupted by this module: hook adapters must supply their own deadlines. No retry loop is present.

Stable document+URL keys, source metadata, membership, plan identity and manifest/config fingerprint identify preparation changes. `unchanged_bytes` means identical captured records, membership and plan/config at those configured URLs, never no legal amendments or current law. Fixed source URLs do not discover new acts or repository version URLs; adding a source requires a separately reviewed manifest/config update. `force_revalidate=True` prepares downstream stages even when bytes match.

Hooks are server-injected `SK03`, `SK04`, `SK06` functions receiving `{hook, stage, changed_sources, removed_sources, sources, plan_changed, previous_release, foundation_root}`. They must prepare local artifacts without modifying live tables, index, services or published state, then return `{status: 'validated', artifact_path: relative_path, sha256: actual_hash, mode: 'real'|'fixture'}`. Missing hooks leave `pending_validation` and persisted backlog. Invalid artifacts fail closed. The runner does not implement legal comparison, vector rebuild or Genie curation on their behalf. Mode and verdict are trusted backend assertions, not independent validation. No human approval gate is added to conversation; operational validation is separate.

State contains append-only SK02 content objects, immutable-by-hash release manifests, prepared artifacts checked on every `current()`, terminal run records, `backlog.json`, `last_attempt.json`, `last_success.json` and an atomic `current.json` pointer. Repeated completed run IDs return the same terminal record without refetching only for the same plan ID and manifest/config fingerprint; mismatches raise RUN_PLAN_CONFLICT. Use a fresh ID for a new attempt. File publication uses replace + fsync; an exclusive POSIX flock serializes local runs and releases on process exit. Stable error codes and no exception strings enter result records; cost remains null. Failed attempted captures do not advance success freshness. Sealed reuse explicitly does not establish remote freshness.

The lock requires a filesystem with reliable local POSIX flock semantics. It is not a distributed lock for Databricks Volumes/object storage or multiple drivers. The PAUSED job template adds max_concurrent_runs=1, but that alone cannot serialize other callers. Cloud activation still needs a validated shared lock/store, authorized existing cluster/workspace paths and real prepared hooks. Template placeholders are intentional and must not be passed directly to Jobs create. The delivered notebook allows only reuse_sealed; it executes actual six-PDF SK02 work and copied-state fault recovery without changing the project corpus.

Recovery procedure: retain the previous pointer and the entire compatible state tree. Prepare in a copied tree, inject failure before publication and confirm `current()` and originals' hashes stay unchanged. To restore an older production release, separately validate its artifacts and compatible backend data before a controlled pointer switch. This component demonstrates local data/pointer preservation only; it does not claim cloud rollback, database recovery or whole-agent E2E.

Pointer hardening v0.1.4: current.json must be a closed object containing lowercase hex64 release_id and sha256. Parsing/type/path validation happens before reading any release destination; resolved symlink escapes are rejected. Tests restore the prior pointer after corruption and verify six-PDF operation in a relocated snapshot with original-repository reads denied.

Refresh hardening v0.1.5: reject all preexisting state-tree symlinks before lock/writes. Atomic files and locks use no-follow descriptor traversal; temporary publication and replace are relative to the pinned parent descriptor. Trusted preparers must not mutate published state or introduce symlinks. This is local containment, not isolation against a hostile process allowed to rename the whole state tree concurrently; filesystem permissions remain required.

`publication_committed` records pointer visibility. `published_cleanup_pending` means publication succeeded but cleanup (or a post-replace durability operation) failed; it must never imply preservation of the previous pointer. `last_success` records technical success, not clean completion or remote freshness. Retry using a fresh run ID and force_revalidate to complete preparation/cleanup; inspect pending backlog and previous terminal record. Pre-commit failure remains failed with the old pointer. If failure occurred after replace but before fsync, visibility is observed but crash durability is not established.

`real_preparation_completed` summarizes trusted hook mode labels only. `production_validated` stays false for compatibility and `e2e_acceptance` stays not_evaluated. These labels cannot certify production or institutional approval.
