# SK12 / CreatorZ — sesión OAuth explícita 200

Capacidad acotada: autenticar el ejecutor en un único proceso mediante las APIs públicas de Python SDK 0.102.0, conservando SessionCredentials en memoria. Entrada autorizada: mismo host `https://dbc-0410b264-20c7.cloud.databricks.com`, cliente `databricks-cli`, scopes `offline_access all-apis`. El coordinador confirmó el comando anterior del usuario `databricks auth login --host https://dbc-0410b264-20c7.cloud.databricks.com --profile databricks-ai-engineer-aws`, sin scopes personalizados: equivale a los defaults oficiales, sin ampliar grants ni duración solicitada.

Código: `deployment/oauth_session200.py`. API: `authenticate(publish_authorization_url, timeout_seconds=180) -> Config`; el ejecutor debe recibir/retener esa instancia, sin recrear Config desde el perfil. `protected_authorization_url(path)` permite publicar únicamente URL de autorización en archivo nuevo0600, excluyente y efímero. CUA navega esa URL; el módulo nunca abre navegador. Tokens, refresh tokens, código y callback permanecen en memoria, sin repr, inspección o serialización. Ningún efecto por import.

Flujo: bind loopback127.0.0.1:8020 → OAuthClient.from_host con host/cliente/scopes explícitos → initiate_consent → publicar Consent.authorization_url → recibir un callback → validar forma y delegar verificación state/exchange al SDK → Config(credentials_strategy=session). Puerto8020/redirect http://localhost:8020 coinciden con GoCLI y PythonSDK. Omitir entorno DATABRICKS_/ARM_/AZURE_ al lanzar el proceso; el módulo rechaza valores heredados y no toca el entorno global ni HOME. Host explícito sin perfil evita lectura de configuración global. No se usa TokenCache ni auth CLI.

Reglas: no imprimir Config, SessionCredentials ni excepciones proveedor; usar AuthSessionError seguro. No enviar URL de callback a tools/logs; HTTP handler no registra requests. No publicar el enlace de autorización fuera del archivo efímero/local CUA. Los errores y timeout borran ese archivo si el llamador usa el context manager. El flujo del usuario sigue siendo autenticación interactiva real; una sesión de navegador existente podría bastar, pero no se presume.

Límites: timeout180s cubre espera de callback, no toda la autenticación; SDK retrieve_token usa requests.post sin timeout configurable por esta API. Supervisor del proceso puede imponer su límite, sin parchear SDK. Callbacks inválidos no producen exchange; forma válida con state erróneo falla antes de request de token. No hay retry automático ni cache persistente; al terminar el proceso se requiere sesión nueva. Configurado para una única misión/host, no herramienta general. No proporciona permisos adicionales de recursos o gasto.
