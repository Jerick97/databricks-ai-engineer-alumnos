# Publicación inicial ejecutable — checkpoint16

API: `load_write_plan(root, publication_id=...)` verifica export002/map/fuentes locales mediante el loader existente, sin reconstruir ni inferir. `preflight(plan)` es exclusivamente local. `sdk_writer(plan, WriterConfig(...), journal, sdk_config=Config(...))` arma servicios oficiales con transporte single-attempt; `publish(certificate_directory=..., registry_directory=...)` ejecuta el camino completo. Plan sellado: `runs/sk06-publication-writer-016-plan.json`; notebook: `notebooks/sbs-radar-genie-publication.ipynb`.

El perfil inicial es **instalador/publicador propietario ya existente** de catálogo y esquema. No es el Job writer ni la aplicación lectora; no exige conceder propiedad de catálogo a esos SP. Comprueba Me/ID exacto, propietario actual, schema UUID fijado, CAN_USE/CAN_MANAGE/IS_OWNER directo observado y warehouse RUNNING. No resuelve grants mediante nombres de grupo supuestos. Otro actor requiere un perfil distinto revisado; no se amplían sus permisos aquí. El esquema existente `neptuno_manuel_arguelles.sbs_radar` tiene ID `ff244e9c-7d34-4c2d-8d74-a33292cd5f2c`; la observación histórica no acredita acceso actual.

Las ocho tablas deben estar ausentes antes de la primera escritura. Se emite CREATE TABLE sin IF NOT EXISTS, con publication_id y snapshot como propiedades, y una INSERT con parámetros STRING tipados por tabla; NULL y booleanos son constantes generadas. El contenido normativo nunca se concatena como SQL. Hay 164 filas: 6 documentos, 6 versiones, 141 disposiciones, 2 pares, 3 cambios, 3 evidencias, 1 revisión IA y 2 procesos ficticios. Granularidad, anotaciones y hashes originales se conservan. No hay CREATE SCHEMA, control-table DDL, grants, DROP, overwrite, MERGE ni arranque de compute.

Cada mutación guarda intención durable antes de POST bajo journal append-only con lock y sin symlinks. Un fallo ambiguo **no se reenvía**. Se observa identidad/propiedades y se compara el readback íntegro con el resultado exacto. Tabla nueva debe estar vacía antes de insertar. Respuesta perdida con efecto confirmado puede continuar; ausencia de efecto es `MUTATION_UNCONFIRMED`, no autorización para repetir. La recuperación requiere conservar el journal servidor; su pérdida no autoriza adoptar tablas existentes. No hay rollback destructivo automático: ante fallo quedan tablas propias parciales y registro ausente; antes de cualquier limpieza se deben revisar identidades e historial. No se toca el release ni configuración vigente.

DESCRIBE HISTORY aporta versión real máxima observada y userId del publicador, seguido de SELECT VERSION AS OF y comparación completa. Bajo mantenimiento exclusivo declarado, esta es la versión disponible al corte de cada readback; no se inventa una versión por contar INSERT. Si userId falta, se declina. PublicationReader vuelve a verificar 32 lecturas (DETAIL/HISTORY/SELECT/DETAIL por tabla); HistoryRegistryBuilder consulta los 32 statement IDs observados mediante GET independientes, con SQL/actor/warehouse/estado/tiempos/cache. Solo entonces se almacena certificado v2 y registro local. Un historial no disponible permite reintentar lecturas, nunca mutaciones ya intentadas.

Camino normal: 16 POST de mutación + 64 POST SELECT/DESCRIBE = 80 submissions SQL; 32 GET de Query History aparte. Máximo por instancia: 512 solicitudes HTTP de workspace, 96 lecturas SQL, 3 polls por statement, 64 chunks, 1000 filas/2 MB por resultado, INSERT request compilado <=2 MB; HTTP response <=4 MB. OAuth puede tener tráfico propio fuera de esa cuota. Cuotas limitan trabajo, no precio: coste desconocido. Se comprueba RUNNING antes de cada POST; no existe atomicidad GET+SQL y un cierre externo entre ambos podría activar comportamiento del warehouse. Mantenimiento coordinado es supuesto, no garantía de coste.

Gobernanza `trusted_admin_publisher_observed_v1`: propiedad y metadatos son observaciones actuales; mantenimiento exclusivo, retención y ausencia de ABAC heredada son declaraciones administrativas explícitas con vencimiento. No prueban continuidad histórica ni prevención ABA. El registro no excede ese vencimiento. El publicador owner puede escribir: su prueba no satisface SELECT-only del lector. Configuración del espacio Genie, grants del lector, acceso al historial y binding runtime siguen separados y pendientes; no se crea un espacio ni se declara E2E por publicar tablas.
