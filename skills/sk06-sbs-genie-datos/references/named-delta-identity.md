# Identidad nombrada UC/Delta — experimento 056

El fallo real053 `DELTA_IDENTITY_INVALID` provino de `DESCRIBE DETAIL.location == ""`, mientras UC GET devolvió una ruta no vacía. No se atribuye una causa a esa diferencia. [DESCRIBE DETAIL](https://docs.databricks.com/aws/en/tables/operations/table-details) define id, name y location; [UC Get Table](https://docs.databricks.com/api/uc-tables/v1/get-table) define table_id, metastore_id y storage_location. Esas fuentes no explican el vacío observado ni prueban una relación física entre ambas rutas.

El default `strict_location_v1` conserva igualdad de rutas. La capacidad explícita servidor `uc_managed_named_detail_v1` acepta exclusivamente tablas UC MANAGED/DELTA, identidad UC completa y estable, DETAIL con formato delta, ID no vacío y nombre exacto de la consulta nombrada. Location debe ser cadena vacía o coincidir exactamente con UC; null, campo ausente o ruta contradictoria se rechazan. Repite observaciones UC/DETAIL antes/después; conserva HISTORY, versión fija, readback íntegro/hash y verificación independiente del SQL ejecutado en Query History.

`location_sha256` procede de UC. Cada tabla declara `location_evidence` y si DETAIL estaba vacío o coincidía; vacío implica `physical_location_relation_observed=false`. La igualdad de observaciones antes/después no prueba continuidad ni impide ABA. Exige gobernanza administrativa observada y declarada, con esas limitaciones; no se convierte en assurance estricto.

Uso: pasar `identity_profile='uc_managed_named_detail_v1'` a `sdk_writer` o `PublicationWriter`. Propaga reader, CertificateStore y RegistryAdmin/Builder. Lectores directos deben seleccionar el mismo perfil en CertificateStore y RegistryLookup. DeltaPublication requiere `certificate_identity_profile` explícito, `assurance_profile='trusted_admin_observed_v1'` y una TrustedAdminObservedProbe real del servidor. El registro y certificado deben concordar. Los defaults rechazan certificados del nuevo perfil; no hay fallback automático. No tomar estos valores de una solicitud de usuario.

El perfil es capacidad del lector, no campo WriterConfig: no cambia plan, SQLscope, hash del binding ni renueva autorización. Una continuación conserva journal/config originales y usa admisión temporal/presupuesto acumulado existentes. La prueba local de continuación posterior a ocho INSERT usa 48 SQL adicionales sin CREATE/INSERT repetidos, conserva binding byte a byte y WriterConfig completo. El presupuesto real depende del ledger actual, expiración y polls; 48 fixture no es reserva remota ni promesa de ejecución.

Evidencia: `runs/sk06-delta-profile-056-record.json`, pruebas `tests/unit/test_delta_profile_056.py`. La fixture incluye el resultado real observado, pero los recorridos de integración usan dobles y no certifican publicación cloud. Antes de continuar, revisión SK09 del código congelado e integración explícita en ejecutor vigente; no modificar autorización o journal para ocultar incompatibilidades. No se requiere un nuevo consentimiento por la mera ventana cuando la autorización autónoma vigente cubre la continuación.
